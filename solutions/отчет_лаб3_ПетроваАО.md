## Часть 3\. Права на файлы и каталоги

Риск SUID-файла с владельцем root заключается в возможности повышения привилегий. Любой пользователь системы, запустив такой файл, получает права root на время выполнения программы. Если в программе есть уязвимость (например, возможность открыть произвольный файл или выполнить произвольную команду), злоумышленник может получить полный контроль над системой. В нашем примере nano\_suid с владельцем root позволяет любому пользователю читать и изменять любые файлы в системе, что приводит к компрометации всей системы.

## Часть 6\. Аудит безопасности в скрипте инвентаризации

script\_passport\_v3.sh

```
#!/bin/bash

die() {
 echo "Ошибка выполнения $1" >&2
 exit $1
}

usage() {
   echo "Использование: $0 [ИМЯ_ФАЙЛА_ОТЧЁТА]"
   echo "По умолчанию отчёт сохраняется в PASSPORT/inventory.txt"
   echo "Скрипт требует прав root или пользователя с рабочим sudo."
   echo "Коды ошибок: 100 - права, 200 - функция, 250 - утилита"
   echo "Для вывода этой справки добавьте ключ -h или --help"
}


check_privileges () {
 if [ "$EUID" -ne 0 ]; then
   echo "У вас недостаточно прав для запуска скрипта"
   exit 100
 fi
}

check_tool() {
 if [[ $(which "$1") == "" ]]; then
   echo "Команда $1 не найдена, перед запуском необходимо её установить"
   die 250
 fi
}

log_run() {
 cur_date=$(date +"%Y.%m.%d")
 echo "Скрипт был запущен: $cur_date" >> PASSPORT/log/report.log
 echo "Используемая версия скрипта: V3" >> PASSPORT/log/report.log
 echo "===================================" >> PASSPORT/log/report.log
}

write_section() {
 local title="$1"
 local content_file="$2"
 echo "=== $title ===" >> "$name".txt
 if [ -s "$content_file" ]; then
   cat "$content_file" >> "$name".txt
 else
   echo "Нет данных" >> "$name".txt
 fi
 echo "" >> "$name".txt
}

clean_up() {
 find . -type f -name "*.tmp" -delete
}

mkdir -p PASSPORT/log
mkdir -p PASSPORT/tmp

if [[ $1 != "" ]]; then
 name=$1
else
 name="inventory"
fi

if [[ "$1" == "-h" || "$1" == "--help" ]]; then
 usage
 exit 0
fi

check_privileges
log_run

date > PASSPORT/tmp/date.tmp
hostname > PASSPORT/tmp/hostname.tmp
whoami > PASSPORT/tmp/whoami.tmp
who > PASSPORT/tmp/who.tmp
pwd > PASSPORT/tmp/pwd.tmp
ls -la > PASSPORT/tmp/ls.tmp

#проверка наличия утилит
check_tool lspci
check_tool dmidecode
check_tool lscpu
check_tool lastlog2
check_tool uname
check_tool lsmem

#ядро и разрядность
uname -a > PASSPORT/tmp/uname.tmp
uname -m > PASSPORT/tmp/arch.tmp

#версия ОС
cat /etc/os-release > PASSPORT/tmp/os.tmp

#инфо о процессоре
lscpu > PASSPORT/tmp/lscpu.tmp

#инфо о памяти
lsmem > PASSPORT/tmp/lsmem.tmp

#устройства PCI
lspci > PASSPORT/tmp/lspci.tmp

#инфо о мат плате и биос
dmidecode -t baseboard > PASSPORT/tmp/baseboard.tmp
dmidecode -t bios > PASSPORT/tmp/bios.tmp

#пользователи (root и UID >= 1000)
> PASSPORT/tmp/users.tmp
# getent passwd выводит список всех пользователей, разделенный двоеточиями (имя:пароль:UID:...)
# awk отбирает строки, где 3-е поле (UID) равно 0 или больше/равно 1000 (но меньше 65534, чтобы отсечь nobody)
USERS=$(getent passwd | awk -F: '$3 == 0 || ($3 >= 1000 && $3 < 65534) {print $1}')
for user in $USERS; do
   echo "Пользователь: $user (UID: $(id -u "$user"))" >> PASSPORT/tmp/users.tmp
   echo "  Группы: $(id -nG "$user")" >> PASSPORT/tmp/users.tmp

   # Последний вход
   # lastlog -u показывает последний вход; tail -n 1 отрезает шапку таблицы, оставляя только строку с данными
   login_info=$(lastlog2 -u "$user" | tail -n 1)
   echo "  Последний вход: $login_info" >> PASSPORT/tmp/users.tmp

   # chage -l показывает информацию о пароле; grep оставляет строку со сменой пароля; cut берет текст после двоеточия
   pwd_changed=$(sudo LC_ALL=C chage -l "$user" | grep -E "Last password change" | cut -d: -f2 | xargs)
   echo "  Последняя смена пароля: ${pwd_changed:-Нет данных}" >> PASSPORT/tmp/users.tmp
   echo "-----------------------------------" >> PASSPORT/tmp/users.tmp
done

#параметры sshd
sshd -T | grep -E "^(permitrootlogin|port|logingracetime|maxauthtries|passwordauthentication|pubkeyauthentication) " > PASSPORT/tmp/sshd.tmp

#топ 5 процессов по памяти
ps -eo pid,ppid,user,%mem,cmd --sort=-%mem | head -n 6 > PASSPORT/tmp/top5.tmp

#подозрительные учетные записи
> PASSPORT/tmp/suspicious.tmp
echo "Пользователи с UID 0 (кроме root):" >> PASSPORT/tmp/suspicious.tmp
awk -F: '$3 == 0 && $1 != "root" {print $1}' /etc/passwd >> PASSPORT/tmp/suspicious.tmp
echo "Пользователи с пустым паролем:" >> PASSPORT/tmp/suspicious.tmp
sudo awk -F: 'length($2) == 0 {print $1}' /etc/shadow 2>/dev/null >> PASSPORT/tmp/suspicious.tmp

#файлы с suid
find /usr/bin /usr/sbin -type f -perm -4000 > PASSPORT/tmp/suid.tmp

cat > "$name".txt << EOF
===========ДИАГНОСТИЧЕСКИЙ ОТЧЕТ О СИСТЕМЕ (v3) ===============
```

## Вопросы и задания

1. *Зачем при создании SSH-ключа предлагается задать парольную фразу и от какой угрозы она защищает?*
   Парольная фраза защищает от угрозы кражи закрытого ключа: если злоумышленник получит доступ к файлу закрытого ключа, он не сможет использовать его для аутентификации на сервере без знания этой парольной фразы.
2. *Зачем при первом подключении по SSH клиент показывает отпечаток ключа сервера и просит подтвердить его? Что произойдёт, если отпечаток изменится?*
   При первом подключении клиент сохраняет отпечаток ключа сервера в файл \~/.ssh/known\_hosts. При последующих подключениях клиент сверяет текущий отпечаток с сохранённым. Если отпечаток изменится, клиент выдаст строгое предупреждение и заблокирует подключение, так как это может означать, что вы подключаетесь к поддельному серверу, а не к настоящему, либо ключи на сервере были переустановлены.
3. *Если у двух пользователей одинаковые пароли, можно ли понять это по /etc/shadow? Почему?*
   Нет, нельзя. Хеш пароля в файле /etc/shadow генерируется с использованием случайной «соли». Даже если два пользователя задали абсолютно одинаковый пароль, из\-за разной случайной соли итоговые хеши будут совершенно разными.

5. *Почему для удаления файла нужны права на каталог, а не на файл? Какие изменения вносит установка sticky bit на каталог?*
   Файл в Linux — это просто запись (имя и указатель на данные) внутри каталога. Удаление файла означает изменение содержимого каталога (удаление этой записи), поэтому требуются права w (запись) и x (доступ) именно на родительский каталог, а не на сам файл.
   Установка sticky bit на каталог изменяет это правило: даже если у пользователя есть права w и x на каталог, он сможет удалить или переименовать файл внутри него, только если является владельцем этого файла, владельцем каталога или root.
6. *Приведите команду setfacl... Как решить с помощью ACL задание 3 из Части 3?*
   Команда для выдачи всех прав конкретному пользователю:
   `setfacl -m u:имя_пользователя:rwx имя_файла`
   Задание 3 (3) \- каталог /DATA/sec2: u1 может всё, u4 и u5 только читать, остальные не могут ничего
   `chmod 000 /DATA/sec2`
   `setfacl -m u:u1:rwx,u:u4:r-x,u:u5:r-x /DATA/sec2`
7. *Чем различаются su, su \- и sudo? Почему в Debian рекомендуют sudo?*
   su: переключает на другого пользователя, запрашивая пароль целевого пользователя, но сохраняет часть переменных окружения текущего пользователя.
   su \-: выполняет полноценный вход с загрузкой полного окружения (домашний каталог, переменные среды) целевого пользователя, как при обычном логине.
   sudo: выполняет одну конкретную команду с правами другого пользователя (обычно root), запрашивая пароль текущего пользователя.
   Почему рекомендуют sudo: это безопаснее (пароль root не нужно сообщать другим), удобнее (не нужно выходить из своей сессии) и обеспечивает лучший аудит безопасности, так как каждое использование sudo записывается в системный журнал.
8. *Удалось ли вам обойти ограничение sudo из Части 5? Почему правила с подстановочными знаками опасны?*
   Ограничение можно обойти, если в правиле sudoers использованы подстановочные знаки (например, /usr/bin/passwd \*). Это позволяет пользователю передать в качестве аргумента слово root (команда sudo passwd root) и сменить пароль суперпользователя.
   Правила с подстановочными знаками считаются опасными, потому что они дают пользователю возможность передать непредусмотренные аргументы, что может привести к повышению привилегий или изменению системных файлов, нарушая принцип наименьших привилегий.
   Поэтому я в работе использовала выражение `^[a-zA-Z]+$`
9. *Чем отличается SIGTERM от SIGKILL? Какой из них процесс может перехватить?*
   SIGTERM (15): это «вежливая» просьба завершиться. Процесс может перехватить этот сигнал, сохранить данные, корректно закрыть открытые файлы и завершить работу.
   SIGKILL (9): убивает процесс принудительно и немедленно на уровне ядра. Процесс не может перехватить, заблокировать или игнорировать этот сигнал.
10. *Что происходит с процессом, запущенным через &, при закрытии SSH-сессии, и почему nohup меняет это поведение? Почему PPID стал другим?*
    Современный bash по умолчанию не завершает фоновые процессы при завершении сессии, они “сиротеют” и их принимает к себе ядро, поэтому и меняется PPID.
11. *Что такое зомби-процесс? Можно ли его убить командой kill \-9 и почему?*
    Зомби-процесс (состояние Z в ps) — это процесс, который уже завершил своё выполнение, но его запись в таблице процессов ещё не удалена, потому что родительский процесс не считал его код возврата (не вызвал системный вызов wait).
    Убить зомби командой kill \-9 нельзя, потому что он уже мёртв (не выполняет никакой код). Чтобы убрать зомби, нужно отправить сигнал SIGCHLD родительскому процессу или завершить сам родительский процесс (тогда зомби усыновит systemd, который его корректно «похоронит»).
12. *Чем отличается вывод sshd \-T от строк, найденных в sshd\_config через grep?Приведите пример параметра, у которого они различаются.*
    grep по файлу sshd\_config показывает только то, что явно написано в этом конкретном файле (или закомментировано). Команда sshd \-T показывает эффективные (итоговые) значения, которые сервер реально использует, с учётом всех включённых файлов из каталога /etc/ssh/sshd\_config.d/ и встроенных значений по умолчанию.
    Пример: В /etc/ssh/sshd\_config может быть написано \#PermitRootLogin yes (закомментировано, действует значение по умолчанию prohibit-password), а в файле /etc/ssh/sshd\_config.d/custom.conf написано PermitRootLogin no. grep по основному файлу покажет комментарий или ничего, а sshd \-T покажет реальное действующее значение: permitrootlogin no.
13. *Какой риск возникает, если владельцем исполняемого файла будет root и на этот файл будет установлен suid?*
    Это создаёт критическую уязвимость безопасности. Любой пользователь системы, запустивший такую программу, будет выполнять её с полными правами суперпользователя (root). Если в коде этой программы есть ошибка (баг или уязвимость), злоумышленник может эксплуатировать её, чтобы выполнить произвольные команды от имени root и полностью скомпрометировать (взломать) систему.
